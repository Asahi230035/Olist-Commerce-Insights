# Olist 电商数据分析项目｜数据处理与分析方法

## 1. 项目方法概述

### 1.1 分析目标

本项目基于 Olist 巴西电商平台公开交易数据，构建统一、可复现的商业数据分析基础，为后续平台经营、商品销售、客户价值及配送体验分析提供支持。

数据处理遵循以下原则：

**原始数据保留 → 数据质量检查 → 标准化处理 → 业务粒度建模 → 指标验证 → 业务分析。**

数据异常并不必然意味着记录无效。因此，本项目优先采用质量标记、条件筛选和标准化视图，而不是直接修改或删除原始记录。

### 1.2 技术架构

| 技术 | 主要用途 |
|---|---|
| Python | 数据读取、数据检查及数据库导入 |
| pandas | 数据初检、缺失值及重复值检查 |
| MySQL 8.4 | 数据存储、清洗及关系建模 |
| SQLAlchemy / PyMySQL | Python 与 MySQL 数据交互 |
| SQL Views | 数据标准化与分析视图 |
| Jupyter Notebook | 后续统计分析与可视化 |

数据库名称：`olist_analysis`

## 2. 数据来源与处理流程

### 2.1 数据来源

数据集：Brazilian E-Commerce Public Dataset by Olist

来源：Kaggle

地址：https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce

数据包含订单、商品、支付、评价、客户、商家及地理位置等信息，共九张原始数据表。

本项目使用公开数据集中的历史订单记录，不假定其覆盖平台的完整经营历史。

### 2.2 数据导入

通过 Python 读取原始 CSV 文件，使用 SQLAlchemy 与 PyMySQL 将数据分批导入 MySQL。

导入过程采用以下策略：

| 处理项目 | 方法 |
|---|---|
| 外键依赖 | 按关联关系确定导入顺序 |
| 大规模数据 | 分批读取与写入 |
| 时间字段 | 转换为 MySQL DATETIME |
| 缺失数据 | 转换为数据库 NULL |
| 邮编前缀 | 使用字符串类型保留前导零 |
| 重复导入 | 检查目标表是否已有数据 |
| 导入验证 | 对比 CSV 与 MySQL 记录数 |

九张表的记录数量已全部通过一致性检查。

记录数一致不代表所有字段值均已完成逐项核对，因此后续分析继续保留必要的质量检查。

## 3. 数据质量检查方法

数据质量检查覆盖完整性、唯一性、参照完整性、业务合理性与时间逻辑。

### 3.1 完整性检查

通过 pandas 的 `isnull()` 和 SQL 的 `IS NULL` 检查字段缺失。

缺失值按照业务含义分类处理。

例如，未送达订单缺少实际签收时间通常属于正常业务缺失；已送达订单缺少签收时间则需要标记。

对于评价表，评论标题与正文允许为空，不因文本缺失而删除有效评分。

### 3.2 唯一性检查

根据各表实际数据粒度选择主键。

| 数据表 | 唯一标识 |
|---|---|
| orders | order_id |
| customers | customer_id |
| products | product_id |
| sellers | seller_id |
| order_items | order_id + order_item_id |
| order_payments | order_id + payment_sequential |
| order_reviews | review_id + order_id |

地理位置原始表使用数据库自增代理主键 `geo_id`。

评价表中的 `review_id` 并不唯一，不能直接作为单字段主键。

### 3.3 参照完整性检查

通过关联字段检查订单、客户、商品、商家、支付及评价之间的匹配情况。

已验证的主要业务关联具有完整的非空键匹配关系。

商品类别翻译存在少量未匹配记录，因此该关联允许缺失，不采用会删除未匹配商品的内连接策略。

### 3.4 金额检查

对商品价格、运费及支付金额进行空值与负值检查。

已完成的检查没有发现缺失金额或负金额。

但金额字段通过基础检查不代表所有金额均已完成业务对账。商品金额、运费及支付金额仍需按照不同指标口径计算。

## 4. 订单时间标准化

### 4.1 已发现的异常

| 异常类型 | 记录数 |
|---|---:|
| 已送达但缺少实际签收时间 | 8 |
| 已取消但存在实际签收时间 | 6 |
| 交付承运商早于购买时间 | 166 |
| 实际签收早于交付承运商 | 23 |

异常类型之间可能存在交集，不能直接将数量相加作为不同异常订单的总数。

### 4.2 异常处理原则

所有原始订单均保留。

通过 `v_orders_clean` 增加质量标记，并根据分析场景判断记录是否有效。

总配送时长要求购买时间与签收时间完整，且签收不早于购买。

承运商运输时长还要求承运商交接时间有效、交接不早于购买且签收不早于交接。

### 4.3 配送时长

采用购买至实际签收的时间差：

`delivery_days = TIMESTAMPDIFF(SECOND, purchase_time, delivery_time) / 86400`

结果保留两位小数。

该字段表示自然时间跨度，不是工作日数量。

### 4.4 延迟配送

若实际签收日期晚于预计送达日期，则标记为延迟。

采用日期比较，而不是精确时间比较。

无法判断延迟状态的记录保留为 NULL，不强制归类为按时。

### 4.5 时间异常的局限性

仅依据现有数据无法确定异常时间的真实产生原因。

可能涉及记录错误、异步系统处理或业务流程差异，因此不对原始日期进行主观修正。

## 5. 商品数据标准化

### 5.1 商品类别处理

商品类别首先通过翻译表进行英文标准化。

已发现：

| 数据问题 | 商品数 |
|---|---:|
| 类别缺失 | 610 |
| 存在原始类别但缺少翻译 | 13 |

处理规则：

| 情况 | category_label | category_status |
|---|---|---|
| 有有效翻译 | 英文类别 | valid |
| 原始类别缺失 | unknown | missing_category |
| 原始类别存在但无翻译 | 保留葡萄牙语原文 | missing_translation |

保留全部商品，避免类别缺失造成交易金额丢失。

### 5.2 商品尺寸处理

通过 `is_valid_dimension` 标记商品重量、长度、宽度和高度是否均为正数。

只有尺寸完整有效的商品才能直接用于体积、重量相关分析。

不使用均值或其他统计量自动填补缺失尺寸。

## 6. 评价数据标准化

### 6.1 评分有效性

有效评分范围设为 1–5 分。

现有 99,224 条评价记录全部满足评分有效性要求。

### 6.2 文本完整性

评价标题及正文分别使用 `has_review_title` 和 `has_review_message` 标记。

缺少文字的评分仍参与评分分析。

### 6.3 重复评价关系

数据检查发现：

| 指标 | 数量 |
|---|---:|
| 评价记录 | 99,224 |
| review_id 重复数量 | 814 |
| 存在多条评价的订单 | 547 |

不直接删除重复评价 ID 对应的记录。

对于订单级满意度，先按 `order_id` 聚合有效评分，再与订单主表关联。

一个订单的多条有效评分采用算术平均值作为订单评分。

## 7. 地理位置标准化

### 7.1 原始数据特点

| 指标 | 结果 |
|---|---:|
| 地理位置记录数 | 1,000,163 |
| 唯一邮编前缀数 | 19,015 |
| 完全重复记录数 | 261,831 |
| 对应多个城市的邮编 | 550 |
| 对应多个州的邮编 | 8 |

同一邮编存在多条记录，因此不能直接通过邮编将完整地理位置表关联至客户或订单表。

### 7.2 标准化方法

`v_geolocation_clean` 采用每个邮编前缀一行的粒度。

处理流程为：

**位置记录去重 → 城市与州名称标准化 → 候选地区统计 → 代表地区选择 → 质量标记。**

对完全相同的标准化位置组合进行去重。

随后按邮编、城市和州组合统计不同坐标记录数量，选择记录数量最多的组合作为代表地区。

如出现并列，按照州和城市名称排序，以保证选择过程可重复。

代表经纬度采用选中组合中去重坐标的平均值。

### 7.3 地区质量标记

| 状态 | 含义 |
|---|---|
| consistent | 邮编对应的原始城市和州信息无多值冲突 |
| multi_city | 邮编对应多个城市名称 |
| multi_state | 邮编对应多个州 |

当同时存在城市和州冲突时，优先标记 `multi_state`。

### 7.4 方法局限性

出现频率最高的地区组合不一定对应真实行政位置。

原始记录中的城市名称还可能存在拼写或表达差异。

经纬度的基础合法范围检查不等于严格的巴西境内地理校验。

因此，标准化结果适用于本项目的基础地区关联，但不应直接视为高精度地理编码结果。

## 8. 标准分析视图设计

### 8.1 建模原则

所有核心分析视图均明确业务粒度。

多条支付、多条商品明细和多条评价不能直接按订单 ID 同时关联后计算金额。

应先按订单聚合，再进行关联。

### 8.2 订单级分析视图

视图：`v_order_analysis`

**粒度：一行代表一个订单。**

整合订单、客户、商品金额、支付金额、评价及配送质量信息。

已通过以下验证：

| 检查项 | 结果 |
|---|---:|
| 记录数 | 99,441 |
| 唯一订单数 | 99,441 |
| 重复订单 | 0 |
| 商品金额汇总 | R$13,591,643.70 |
| 支付金额汇总 | R$16,008,872.12 |

### 8.3 商品明细级分析视图

视图：`v_order_item_analysis`

**粒度：一行代表一个订单商品明细。**

用于商品类别、商家及地区销售分析。

通过 `(order_id, order_item_id)` 保证明细唯一性。

已验证商品金额、运费及合计金额与原始商品明细一致。

### 8.4 客户级分析视图

视图：`v_customer_analysis`

**粒度：一行代表一个 customer_unique_id。**

客户级指标基于订单级视图聚合。

累计商品金额采用已送达订单、不含运费的口径。

客户地区采用最近一笔订单记录对应的城市和州。

已通过客户唯一性、订单数量与金额守恒检查。

### 8.5 地理位置关联规则

客户与商家原始邮编保留为字符串。

需要地理坐标时，关联 `v_geolocation_clean`，不直接关联原始地理位置表。

对于没有匹配邮编的客户或商家，保留业务记录，将地理字段视为缺失。

## 9. 业务指标计算规则

正式指标定义统一参照：

`docs/metrics_definition.md`

### 9.1 经营分析

主要使用订单级视图。

默认采用已送达订单的商品金额作为核心经营规模代理指标，不含运费。

订单量、取消率等指标按照各自定义使用相应的订单状态口径。

### 9.2 商品与地区分析

主要使用商品明细级视图。

品类和地区销售额按已送达订单的商品价格合计计算。

保留未知类别对应的商品金额。

### 9.3 客户分析

主要使用客户级视图。

真实客户通过 `customer_unique_id` 识别。

复购采用至少两笔已送达订单的定义。

RFM 使用最近已送达订单购买时间、已送达订单数量和累计已送达商品金额。

### 9.4 配送分析

根据指标选择相应的配送有效性条件。

购买至签收时长、承运商运输时长和配送延迟率使用不同的有效样本定义。

不因物流时间异常而自动排除订单的全部经营金额。

### 9.5 统计分析

后续涉及相关性、差异检验或回归分析时，应明确样本筛选、变量定义、缺失处理和模型假设。

统计相关性不能直接解释为因果关系。

## 10. 数据处理局限性

### 10.1 历史数据窗口

Olist 数据集覆盖有限的历史订单观察期。

不同时间段可能存在订单记录不完整或业务状态尚未最终确定的问题。

跨月比较需要检查首尾月份的完整性。

### 10.2 用户行为数据不足

数据集不包含完整的浏览、点击、加购与曝光事件。

因此不能直接衡量真实流量转化率、完整用户行为漏斗或平台 MAU。

### 10.3 财务数据不完整

缺少完整的退款、佣金、成本和利润数据。

因此商品交易额不能直接解释为平台收入，支付记录金额也不能直接视为最终净收入。

### 10.4 样本代表性

公开数据集未必覆盖平台全部业务。

分析结论原则上只针对数据集观察范围，不直接推广到整个巴西电商市场。

### 10.5 业务状态与观察时间

订单状态反映数据集中的记录状态，不一定能够重建每个历史时点的真实订单状态。

因此，对于取消率、复购率及履约指标，应谨慎解释跨期变化。

## 11. 可复现性与质量保证

### 11.1 SQL 执行顺序

数据库构建按以下顺序进行：

| 顺序 | 文件 | 作用 |
|---|---|---|
| 1 | 01_create_tables.sql | 创建原始数据表 |
| 2 | data_loader.py | 导入 CSV 数据 |
| 3 | 02_data_quality.sql | 执行质量检查 |
| 4 | 03_data_cleaning.sql | 创建标准化视图 |
| 5 | 04_analysis_views.sql | 创建分析视图 |

在重新执行建表或数据导入前，应检查现有数据状态，避免重复导入或误操作。

### 11.2 验证原则

核心验证覆盖：

- 原始记录数量一致性。
- 主键与联合键唯一性。
- 表间关联完整性。
- 标准视图记录数量。
- 订单及客户粒度唯一性。
- 商品金额、运费及支付金额的聚合守恒。
- 异常标记数量与原始质量检查结果一致。
